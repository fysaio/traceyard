# Reproduce and verify acceptance criteria

Use a fresh tester who has no Traceyard source access. Give them the public documentation, the deployed app and client endpoints, and an externally authored npm/Vitest fork with a known failing test and a candidate commit. Record the expected outcome from independent runs before handing the task to the tester.

| Criterion           | Pass                                                                                                                                                                                                                                                                                                              | Fail                                                                                                                                                                               |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First useful result | In under 10 minutes from opening the public quickstart, the tester signs in, connects their own fork, and opens a focused run with the correct failing assertion, full executed SHA, and retained test output. Setup, queue, and install time count.                                                              | Any evidence is missing or wrong, the result takes 10 minutes or longer, or someone has to step in to explain the interface. End the attempt at 15 minutes and record “gave up.”   |
| Less work           | On at least one realistic case, Traceyard reaches the same evidence and candidate verdict as the manual workflow, in less elapsed time or with fewer manual actions, and without any loss in correctness. Time both paths and record actions such as checkout, test runs, and transferring evidence to the agent. | Every Traceyard attempt takes at least as much time and manual effort, or the apparent saving comes from weaker evidence, a wrong result, or omitting part of the manual workflow. |
| Trusted result      | Browser and MCP identify the same baseline and candidate evidence. The developer can open the full executed SHAs, assertion or check outcome, and retained output. The verification state matches the observed runs and lists changed tests or fixtures when applicable.                                          | The evidence is missing, belongs to a different commit or test, disagrees between surfaces, or the state overstates what ran.                                                      |
| Honest limits       | The app distinguishes assertion failures, unsupported repositories, and runs that could not complete. It describes the observed check and offers a next action. A passing candidate has a verdict limited to the recorded test and conditions.                                                                    | The app claims a code-level cause, a definitive repair from a candidate pass alone, a completed test when execution was blocked, or silently falls back to a different revision.   |
| Reason to return    | After the first task, the tester can name another task where they would use Traceyard and point to a concrete saving, such as handing the evidence to an agent without copying it.                                                                                                                                | The tester would use their normal workflow on the next task and identifies no task where Traceyard saves work.                                                                     |

## Expected verification states

| State                    | Required observations                                                                                                                               | Scope                                                                                                           |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Confirmed                | The original failure reproduced, the same recorded test file passed at the candidate commit, and the comparison found no changed tests or fixtures. | The recorded check passed under the tested conditions.                                                          |
| Passed with test changes | The baseline failed and the candidate passed, with changes to tests or fixtures.                                                                    | The check passed with modified test inputs or assertions. Show the changed paths for review.                    |
| Still failing            | The candidate run reports an assertion failure in the recorded check.                                                                               | Show the observed candidate assertion and whether it matches the original when the evidence distinguishes them. |
| Inconclusive             | The original failure did not reproduce, recorded runs indicate a flaky result, or required execution or comparison evidence is unavailable.         | Explain which evidence is missing or inconsistent and show what the user can do next.                           |

Use the same test file and commits for the baseline without Traceyard. Start both paths with the same information and prerequisites. Record time to first useful result, total elapsed time, manual actions, exact points of confusion, and the verdict. Keep authenticated live evidence, local checks, and previously recorded runs distinct.
