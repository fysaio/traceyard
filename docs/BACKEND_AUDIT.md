# Traceyard backend audit

Traceyard’s core job is to turn a developer’s question about a failure into observed evidence, then use the original failing test to check a proposed fix. The web app and the MCP connection should reach the same records. A developer should be able to connect the agent before choosing a repo, approve access when work starts, and see exactly what ran.

The supported path exists today. A developer can authorize a connected repo, dispatch focused Vitest work, read a result tied to a source revision, and verify a pushed candidate against retained evidence. GitHub login, app- and MCP-launched tests, and workflow execution were exercised in production in the preceding releases. The complete connect-first authorization and revocation flow passed browser CI. This is a usable path for supported repositories. It still depends on a configured executor and an eligible test, and there is no measured agent token or latency comparison behind the product claim.

## What this pull request removes

- Twenty-one worker-internal functions without callers, including unused run transitions, dispatch and quota mutations, and overlapping event queries. Active writes stay in the paths that enforce transaction and retry semantics.
- Full-detail reads from the status and evidence paths. Status previously made seven investigation/project queries and now uses one. Evidence previously made eight and now uses one. These counts exclude shared transport and authentication work.
- Session storage writes on unauthenticated health probes. Health continues to check D1 and return the release revision. Clients that need a guest cookie can obtain it from `/api/auth/session`.

## What would establish the remaining vision

1. Run a clean onboarding acceptance with a second repository and a supported failing test. Measure time from initial connection to the first observed result, including installation, workflow approval and dispatch. Capture which step caused any block.
2. Verify a real pushed repair that leaves the reproducer unchanged. Separately test unavailable, private-dependency, and unsupported test setups with an actionable explanation. A GitHub job completing is insufficient evidence without its test report.
3. Capture run latency, D1 reads and executor time for repeat polling, evidence retrieval and verification. Compare before and after using the same input and runner. Gather usage evidence for the optional product surfaces before proposing any retirement.

This pass reviewed the backend entry points, identity and project boundaries, repository checks, investigation and verification services, workflow dispatch and finalization, integrations, retention, and release checks. It used repository references, existing tests, and recent production evidence. It did not infer customer usage from source code. Frontend layout and navigation are a separate audit.
